Found 2026-08-12 while verifying #59's first ProducerScope, and it is the SAME defect class as #58: framework state whose only writer lives on a code path a port with its own frame loop never enters.

MEASURED. First capped native-leg run after the scope landed (PSXPORT_SPYRO_FRAME_LOOP=1, native leg, PSXPORT_NATIVE_FRAMES=3000, log scratch/logs/prod59_run2.log):

    [producers]   guest   0x8007CD38  native 1378  guest 0  frames 1 (f0..f0)  titlefx:spriteEmit

1378 prims over `frames 1`. The independent counter in the producer itself (`PSXPORT_DEBUG=titlefx`, one line per call) shows 1281 producer calls in that run, so the row's frame span was wrong by three orders of magnitude.

CAUSE, not a guess: `census_frame(c)` (external/psxport/runtime/recomp/census_frame.h:23) returns `c->game->timing.logicFrame`, and the ONLY writer of that field anywhere in the framework is `native_step_frame` (runtime/recomp/native_boot.cpp:110) — the framework frame loop this port never enters (C158). So it held 0 for the whole run and every row was stamped f0. The irony is on the record: census_frame.h exists precisely because the feed sites used to stamp rows off the PRESENT counter and 'reported frames 1 (f3..f3) for producers that drew for hundreds of frames'. The stamp was centralised onto a counter that a port owning its loop does not advance, which reproduces the identical field for a different reason.

FIXED PORT-SIDE, one line, in game/core/frame_loop.cpp's loop head: `c->game->timing.logicFrame++`. That loop IS this port's logic frame, which is the counter's documented tick. NOT in producer_run.cpp: that hook runs per PRESENTED FIELD (~1.9 per logic frame here), so advancing it there would re-create the exact present-vs-logic defect census_frame.h was written to remove.

RE-MEASURED after the fix (scratch/logs/prod59_run3.log): `native 1380 frames 697 (f585..f1282)`, and it cross-checks exactly against the producer's own diagnostic — 1282 producer calls of which 585 emitted 0 (the drop-in gate shut), 14 emitted 1, 683 emitted 2 => 1380 prims over 14+683 = 697 frames, and the first non-zero emit is producer call #585 == first_frame f585.

## THE PORT-SIDE FIX WAS ONLY HALF OF THE CONTRACT — the other half is now fixed too

Found in the same verification pass, and it is the SAME root cause, not a new one. The framework's frame loop does **two** things per logic frame:
  * `native_step_frame` sets `c->game->timing.logicFrame = f` (native_boot.cpp:112) — the half fixed above;
  * `native_boot_run` calls `c->rsub.otAttr.beginLogicFrame(f)` (native_boot.cpp:384) — **which this port called NOWHERE.** `grep -rn beginLogicFrame game/` returned 0, and `OtAttr::resetIfNewFrame` is reached from `beginLogicFrame` and from no other caller, so this port drove the span-table reset not at all.

Now driven, one line beside the counter, in `game/core/frame_loop.cpp`: `c->rsub.otAttr.beginLogicFrame(c->game->timing.logicFrame);`.

**IT IS DORMANT TODAY AND THAT WAS CHECKED, NOT ASSUMED — the near-miss is worth recording.** The tempting conclusion was that this is a second, competing cause of the reference leg's 100% span-miss (#61's `guest-origin == span-miss`), since a never-reset table saturating with stale spans is exactly what `beginLogicFrame` exists to prevent. **It is not**, and the code says so: `trackStoreSlow` records a span only for stores inside the packet pool (`if (!pool.known || k < pool.lo || k >= pool.hi) return;`), and `pool_range` returns `known=false` because `packetPoolBase/Stride` are 0 here (`game/core/game_config.cpp:79-80`, issue #56). The span table therefore takes **zero** entries, there is nothing to go stale, and #56 remains the sole sufficient explanation of the span-miss. MEASURED after the change (`scratch/logs/V_refleg_after.log`, reference leg, cap 3000, rc=0): span-miss unchanged at `guest-origin 1485226 + span-miss 1485226`, and the framework prints its own `otattr:warn … packet-pool attribution is STRUCTURALLY BLIND here` confirming the empty table. So this line changes no number today.
**Why land it anyway:** it stops being dormant the instant #56 lands. A filled pool would fill this table with a frame stamp that never advances and no reset ever firing — saturation at `SPAN_CAP`, then every lookup matching a stale span with `fn == 0`, which is the precise failure `beginLogicFrame` was written to remove (ot_attr.h records it: 60 logic frames advanced `s_frame` to 3, 140,153 overflows, guest leg attributed NONE). Fixing #56 on top of that trap would have looked like #56 not working.

FRAMEWORK REMAINDER, NOT FIXED HERE: any other port that owns its frame loop has the same silent 0. spider1 is the known second case (external/psxport/runtime/recomp/producer_db.h names it as the other port that never reaches native_boot_run). The framework cannot detect this itself today — a row stamped `frames 1 (f0..f0)` is indistinguishable from a producer that genuinely drew on one frame, so the honest fix upstream is for the census to REFUSE the stamp (or report it as unknown) when logicFrame has never advanced, rather than printing a plausible span. Do not 'fix' it by having the census fall back to a present counter; that is the defect census_frame.h already removed.

## THE UPSTREAM WARNING EXISTS NOW, AND IT CANNOT FIRE FOR THIS PORT AT THIS PIN — asked and answered

psxport `868aa7e3` (OtAttr: stop reaching through `Core::game` for a frame stamp) added a one-shot warning that says out loud when no frame loop has ever called `beginLogicFrame` on a Core — so the span/watch/per-fn tables are stamped frame 0 and never reset, and a saturated table reads exactly like a busy frame. **Did it fire on a real run here? No — and NOT because this port is healthy.** It cannot fire, because it does not exist at the pin this port records: `grep -rn beginLogicFrame external/psxport/runtime/` at `726d10c9` finds only the declaration and `native_boot.cpp`'s call, with no warn text, whereas the same grep in the dev clone at `868aa7e3+` finds it at `ot_attr.cpp:53-65`. **Reporting "the warning did not fire" as a clean bill of health would have been a negative from a method that could not have produced a positive** — the denominator here is a build that contains no such check.

What that warning WOULD have said, before the fix above: it would have fired, because `game/` called `beginLogicFrame` nowhere. It should stay silent once the pin advances past `868aa7e3`, and **that is the check to run at the next pin bump** — it is the cheapest confirmation that the fix above is wired to the framework's own notion of the contract rather than to this entry's reading of it. Also at `868aa7e3`: `ot_attr.cpp` no longer reads `c->game->gpu.s_frame` at all, so the stale-stamp half of this defect class is closed upstream; at `726d10c9` line 62 still reads it.
