The two nonzero summands are EXACTLY equal, and the same shape is in #58's own note (1718994 = 859497 + 859497) and in C169 (197746 = 98873 + 98873) where it was read as a partition. It is not one: the report presents `prims seen` as a total partitioned by outcome, and a guest prim is counted in it TWICE.

MECHANISM, read from the framework source (external/psxport/runtime/recomp/producer_census.h), not inferred from the equality:
  * `noteGuestOriginPush` (line 170) — called at the render-queue chokepoint (render_queue.cpp emitOrQueue) for every push made while `guestGp0Depth > 0`. Does `mPrimsSeen += prims; mGuestOrigin += prims`.
  * `noteUnattributable(WHY_SPAN_MISS)` (line 173) — reached for the same prim from `GpuState::censusGuestPrim` (external/psxport/runtime/recomp/gpu_native.cpp:2060, the function defined at 2051 and called from 955 / 1070 / 1217), when the packet-pool span table cannot name a submitter. Does `mPrimsSeen += prims; mSpanMiss += prims`.

So on a leg that walks the guest OT, one physical prim raises `mPrimsSeen` twice — via the chokepoint plus whichever of `noteGuest` / `noteUnattributable` the span lookup reaches. `primsSeen()`'s own doc calls it 'the denominator: prims the census was told about' — which is literally true and is exactly the trap: it is a NOTE count wearing a prim count's name, and `primsAttributed()` (line 302) subtracts the classification counters from it, so the identity closes and looks self-consistent.

WHY IT MATTERS even though every number on that line is individually correct: the headline denominator of the DB's own honesty accounting is 2x on every reference-leg run, so any 'X% of prims attributed' computed from it is halved, and a reader comparing a native-leg total (no double count — guest-origin 0) against a reference-leg total on the same workload sees a 2x workload difference that does not exist. This port's real reference-leg prim count for cap 3000 is 1481492, not 2962984.

NOT FIXED HERE — it is framework-side (psxport producer_census.h) and another agent owns that tree this session. Fix direction: `prims seen` must be one increment per prim (count it once, at the chokepoint) with the span-resolution counters reported as a SEPARATE accounting over the same denominator, since 'where did it come from' and 'could its submitter be named' are two orthogonal classifications of one prim and cannot share a partition line. Cheap detector for whoever takes it: a run where guest-origin == span-miss exactly is the tell. **Fix the FUNNEL, not a branch.** `mPrimsSeen` has exactly FOUR writers at this pin, enumerated with `grep -n 'mPrimsSeen +=' producer_census.h`: line 170 `noteGuestOriginPush` (the chokepoint), line 175 `noteUnattributable`, line 515 `note` (reached by `noteGuest` and by the native leg), and line 129 `noteNativeLayer`'s invalid-key branch (the `unscoped-native` path — the NATIVE leg, not a guest prim, so it is not part of this double count and is listed only so a fixer does not miss it). `censusGuestPrim` (2051) has five terminal paths and EVERY one reaches writer 175 or 515 — 2055, 2060, 2094 `noteUnattributable`; 2076, 2105 `noteGuest` — so a guest prim that reached the chokepoint is counted a second time on all five. A fix that only stops the span-miss branch moves the inflation rather than removing it, and would read as fixed on THIS port precisely because #56 keeps every prim in that one branch.

DISTINCT FROM #56, which is why those two counters are equal in the first place: #56 is `GameConfig::packetPoolBase/Stride` being 0 here, so EVERY guest prim lands in span-miss. Filling the pool would move prims from span-miss to attributed and shrink the inflation, but not remove it — the double increment is unconditional.
