# Codemap — what's where, what's done, what's missing

The orientation map: consult it at the START of a task to avoid re-deriving structure, and update it
in the SAME commit that lands or changes a subsystem. A stale map is worse than none — and a
subsystem is marked done only when VERIFIED on real data, never to look better.

Companions: `docs/re-frontier.md` (ordered RE steps: real vs hack), `docs/issues/` (what's been tried
and ruled out), `docs/info/` (claims + instruments ledgers).

**Status vocabulary:** ✅ verified on real data · 🟡 partial (gap named) · 🔬 in progress ·
⬜ not started · ❓ unresolved question · ➖ not applicable to this game ·
🔴 **REGRESSED — it worked and a measurement TODAY says it does not.** Distinct from ⬜ on purpose:
⬜ means nobody built it, 🔴 means the map used to say ✅ and the run disagrees. A row goes 🔴 the
moment a measurement contradicts it, even when the cause is someone else's code and the fix is not
ours to make — a green row above a red gate is the failure this file exists to prevent.

or configuration of Spyro 1.

## Rendering — what actually reaches the screen

- **3D and primitive-drawn screens render correctly** — title and in-level gameplay both verified
  visually (C094, C096). Capture with `PSXPORT_REPL=1` then `shotregion <path> <x> <y> <w> <h>`, and
  inspect with `tools/ppm_look.py` (one distinct colour = empty buffer, thousands = a real frame).
- **UPLOAD-ONLY screens (the SCE + Universal logos) RENDER CORRECTLY** (C149, issue 0043). Measured:
  presents 30/60/120/200 = 2.74% non-black / 252 colours (the SCE card, legible); 300/420 = 27.23% /
  16216 colours (the Universal globe, full 512 width, correct colour). **Do not write a native
  producer for these screens.** They have been black three separate times and every time the cause was
  a one-line framework regression, never a missing producer:
  - issue 0029 / C104 — `render_geom`'s `total == 0` path cleared to black; fixed by honouring
    `GameConfig::preserveVramBackdrop`.
  - issue 0016 / C105 — the display is **24bpp** (`GP1(08)` bit 4) and every decoder read it as 15-bit,
    giving rainbow speckle and two-thirds width. Now honoured in both display-region decoders, the
    present shader and the CPU readback. **`gpu_vk_set_display_depth()`** is the seam.
  - issue 0043 / C149 — `present()`'s empty-batch early-out (`afca817d`) sat **above** `upload_vram`,
    so an upload-only screen — a new picture with zero primitives — never reached `render_geom` at all.
    Fixed by `present_rebuild_decision()` in `external/psxport/runtime/recomp/gpu_vk_present_policy.h`: rebuild when
    EITHER producer changed (primitives submitted, **or** guest VRAM written since the composite was
    built, for a port whose `preserveVramBackdrop` says guest VRAM *is* the picture).
  - issue 0045 / C157 — **THE COMPOSITE IS A PERSISTENT FRAMEBUFFER, and it was not one.** `upload_vram`
    memcpy'd all 1024x512 of guest CPU VRAM over `s_vram_tex` every present; under `vk_path()` the
    guest's polygons never reach CPU VRAM, so that erased the rasterized picture out of the buffer
    about to be displayed — the user's every-other-frame flicker, 10 of every 20 presents a solid
    2-colour fill. Fixed by keeping the rect `gpu_vk_dirty()` already received and uploading ONLY
    those regions: `external/psxport/runtime/recomp/vram_dirty.h` (`VramDirty` / `vram_upload_regions`),
    gated by `external/psxport/tests/test_vram_persistence.cpp`. **`non-black %` cannot see this bug**
    (93.33% on both classes) — use distinct colour count over >=20 CONSECUTIVE presents, windowed.
    The new instrument that located the two buffers is `PSXPORT_DEBUG=rqflush` (**I044**), which prints
    each flush's item count, its re-emit bit and its queue y-range.
  **C099 said the opposite of all this and is `falsified`** (2026-08-04). It read as a live description
  of the renderer for a week after the code under it was fixed, and acting on it "would have meant
  porting a native producer for the logo screens to work around a one-line framework regression".
- **`PSXPORT_DEBUG=presentskip` (I037) is the instrument for this**, and it reports its denominator:
  over 84400 presents Spyro takes `reuse_last` 404 and `rebuild_vram` 33, the rest `rebuild_geom`; both
  non-geometry counts plateau by present ~600, so the fix touches only the boot-logo phase.
- **Two observers, neither complete.** `PSXPORT_GPU_DUMP` reads CPU `s_vram` and sees uploads but no
  VK geometry (I008); the VK readback sees the composited result. A discrepancy between them is the
  expected state, not a bug — pick the observer that matches the question.
- **Native per-vertex depth is mechanically working but covers only ~2.5% of primitives** (C128):
  23281 of 921709 across a full run; 47 frames at 100%, 81 partial, **698 at zero**. Measure it with
  `tools/depth_cov.py` over a whole run and never from one frame — picking a frame because `ndepth`
  reported 3D there selects for success, which is exactly how C125 got falsified. Open: issue 0038
  (the biggest uncovered submitter is `0x800258F0`, multi-path) and issue 0041 / C145 (the cache rolls
  its generation once per FRAME but a generation means one POOL BUFFER; the naive fix serves stale
  depths and depth-culls Spyro out of the frame — the sound fix keys entries by pool-buffer identity).
  **Coverage is not correctness** (C146): do not quote a coverage percentage as a sorted-correctly one.

## Performance — where the time actually goes

Measured, not assumed (`PSXPORT_PROF=1` + `tools/prof_hot.py`, I022):

- **Guest code is only ~5-6% of CPU** (C082). Native ownership buys correctness and architecture,
  not speed — pursue it for that reason, and pick speed targets from the profile instead.
- **The diagnostics layer cost ~10% while doing nothing.** lucent's `channel_enabled` was 6.06% with
  logging switched OFF (a mutex plus a `std::string` per call) — fixed in lucent itself, now 0.33%
  (C084). Every guest store called five out-of-line hooks; `cw_check` + `wwatch_check` were ~4.9% of
  pure call overhead, now inlined away (C085).
- **Result: +12.6% frames in a fixed run, and more of the game reached** — bytes from disc 11.1 →
  13.2 MB, a seventh overlay identified inside the gate's 40s (C087, variance-checked over 3 runs).
- **Then it stopped translating.** A further ~6% removed (`cfg_dbg_generation`, `OtAttr::trackStore`)
  bought NO measurable frames (C089). The run reaches an identical point either way. ~29% of samples
  are outside the binary (driver/loader) and do not shrink, so this workload is likely no longer bound
  by our CPU — unproven. **Do not start another micro-optimisation round without a workload that is
  demonstrably CPU-bound in the code being changed.**
- **Reading a profile: percentages self-rebase.** After a fix, untouched entries' shares RISE because
  the denominator shrank. Only end-to-end throughput sizes a win (C086).
- **`cfg_dbg_generation` is OFF the hot path — nothing calls it.** `OtAttr::trackStore` is now an
  inline `if (!g_otattr_channel) return;` against a `lucent::Channel`, so the per-store cost is one
  relaxed load and a compare instead of the three nested out-of-line calls
  (`trackStore → cfg_dbg_generation → bootstrap_once`) that measured 2.54% of total CPU on their own.
  `cfg_dbg_generation()`/`cfg_dbg_generation_fast()` still exist in `external/psxport/runtime/recomp/cfg.h`
  as dead declarations of the retired `cfg_*` shim (psxport `de187614`). Nothing here is "still
  unexamined" — an earlier version of this section said both that it had been removed and that it was
  outstanding, three lines apart.
- Still unexamined: three of the five per-store hooks.
