Split out of #58 on 2026-08-12, which is now resolved: #58's two stated defects (an unreachable lifecycle, and a silent failure) are both fixed, and this is what is LEFT once the instrument became honest.

MEASURED at psxport pin 7dc380c5: 'grep -rn ProducerScope game/' returns **0** across this entire tree. Tomba2Engine has them in 13 files. A 400-frame capped headless run took the native path ('[render] render path = native — geometry from PC-NATIVE producers, rasterized by the PC rasterizer (SDL_GPU)'), so native producers drew the whole picture and contributed 0 notes to the census. Nothing is broken — the scopes were simply never written.

WHY THIS MATTERS MORE THAN IT LOOKS: the producer DB is the answer to 'which effects have a native producer and which are still substrate'. With no scopes, this port cannot answer that question at all, in either direction. And the failure mode is the dangerous one: a reader glancing at an empty DB could conclude 'no native producers exist' when in fact they draw everything. The framework now says so out loud rather than letting that inference stand, which is the only reason this was findable.

THE WORK, and the rule it must follow (producer_scope.h): key each scope on the GUEST submitter the native draw stands in for — never on a shared dispatcher (it would collapse every per-mode emitter into one meaningless row) and never on a shared submit leaf (it would name the library instead of the effect). Tomba2Engine's game/render/perobj_dispatch.cpp:257 is the worked example, including the DisplayPassGuard discipline that keeps a native draw inside a substrate body from violating the pc_render read-only-overlay invariant.

NOT #56, and they must not be merged: #56 is the GUEST leg unable to attribute because GameConfig::packetPoolBase is 0 (packet pool not RE'd). This is the NATIVE leg having nothing to attribute FROM. Fixing either one alone still leaves the DB unable to COMPARE the two legs, which is its whole purpose — so both are prerequisites for a real spyro producer DB.

DEPENDENCY WORTH KNOWING BEFORE STARTING: the cross-leg join is by nature cross-run (a guest leg never runs native producers; a native leg never GP0-executes guest packets), and it is carried by scratch/producers/claims.txt, which this port has never written. See Tomba2 kanban #91 — that claim file is append-only with no build provenance, so a claim fossilises when a producer's key moves. Do not build spyro's claim set without reading that first.

### Resolution (2026-08-12)
RESOLVED 2026-08-12 at psxport pin 4d218e9f. The port declares its native producer, the census is FED, and 'NEVER FED' is gone from the report.

WHAT LANDED — ONE scope, because exactly one is justifiable in this tree, and a second would have been a guess. `game/render/fx_title_menu.cpp` `SpyroRenderer::spriteEmit` now opens `ProducerScope(&c->rsub.producerScope, 0x8007CD38, "titlefx:spriteEmit")` around its single `push2dQuad`. The render-queue chokepoint has exactly ONE game call site in this whole tree (confirmed again by grep: `push2dQuad`/`drawWorldQuad` appear in no other game file, and `vsync.cpp:230` records that this repo never calls `drawWorldQuad`), so one scope covers 100% of the native prims this port can push — measured `unscoped-native 0`.

THE KEYING, with the three rejected candidates named so the choice is reviewable rather than asserted:
  * 0x8007CD38 CHOSEN — `spriteEmit` IS its transcription (RE'd in scratch/decomp/title_text.c, FUN_8007cd38), one native quad per guest POLY_FT4, same table reads. It is the finest-grained guest fn that SUBMITS, so the guest leg (OtAttr, keyed at the packet-pool store) and this native scope land on the SAME row, which is the whole point.
  * 0x8007CEE4 REJECTED — the stage-13 arm/state machine. It dispatches and submits nothing. Keying a dispatcher is what producer_scope.h forbids, and since the census charges a prim to the INNERMOST open scope, an outer scope here would ALSO mint a permanently 0-prim row that reads as 'a producer that draws nothing'.
  * 0x800168DC / 0x80016784 REJECTED — the front-list AddPrim and the OT walk: the shared submit leaf the whole game funnels through. Keying them names the library instead of the effect.
No `DisplayPassGuard`, and that is a decision: Tomba!2's worked example needs one because its native draw sits INSIDE a substrate body that legitimately writes guest RAM; this producer's entire call chain is port code (frame_loop -> drawFrame -> renderScene -> titleMenuRender -> spriteEmit) and writes no guest memory, while the enclosing frame's env setup (frame_env.cpp) DOES write guest RAM — so arming the per-Core guard here would assert nothing this chain can violate and would fire on the frame's own legitimate guest writes.

TWO DEFECTS FOUND ON THE WAY, both filed rather than folded in here:
  * #60 — `Timing::logicFrame` is never advanced in this port (its only framework writer is `native_step_frame`), so the FIRST verification run reported `frames 1 (f0..f0)` for a producer drawing across 697 frames (CORRECTED 2026-08-12 from 698: `f585..f1282` is a 698-wide SPAN, and it contains exactly one frame that emitted nothing — the producer's own diagnostic in scratch/logs/prod59_run3.log counts 585 `emitted=0` + 14 `emitted=1` + 683 `emitted=2` = 1282 calls, so 14+683 = **697** frames drew and 1380 prims landed. The row itself says `frames 697`; only the prose said 698). Fixed port-side with one line at frame_loop.cpp's loop head; the framework remainder (any port owning its loop, e.g. spider1) is in that entry.
  * #61 — the census's `prims seen` double-counts every guest prim (guest-origin and span-miss both increment it for the same prim), which is why every reference-leg total in this repo's history is exactly 2x, including the figures quoted in #58's note and C169.

IS THE SCOPING COMPLETE, OR JUST 'THE ONE I COULD NAME'? — ASKED 2026-08-12 AND ANSWERED BY ENUMERATION, NOT BY CONFIDENCE. Three independent checks agree that this port has exactly ONE native producer, so there is no second scope to add and any further `ProducerScope` would have to be keyed to a GUESSED address, which producer_scope.h forbids and which is worse than none:
  1. THE API HAS ONE ENTRY POINT AND ONE CALLER. `push2dQuad` is the render queue's only push function (`grep -n '^\s*\(void\|bool\|int\|uint32_t\)\s\+push[A-Za-z0-9_]*\s*(' external/psxport/runtime/recomp/render_queue.h` -> a single hit, line 204), and `grep -rn 'rq\.push\|push2dQuad\|pushTri\|emitOrQueue\|ProducerScope' game/` returns exactly one producing call site — fx_title_menu.cpp:263, the one already scoped. The only other `game->rq` references are CONSUMERS (render_frame.cpp:115 and vsync.cpp:323, both `flush`), not producers.
  2. THE CENSUS ITSELF CERTIFIES IT, which is the check that does not depend on my grep being complete: `prims seen 1380 = attributed 1380 + unscoped-native 0`. `unscoped-native` is precisely 'a prim reached the chokepoint from native code with no scope open', so a zero there means EVERY native prim in the run was attributed. This is the counter that would catch a producer I failed to find, and the sabotage run proves it can be nonzero — narrowing the scope moved 1376 prims into it (`0 row(s) ... unscoped-native 1376`, scratch/logs/prod_sabotage.log).
  3. THE FIVE UNPRODUCED LAYERS ARE NOT CANDIDATES. The run's own `[render:warn] stage 13 native leg is PARTIAL` line names the next five producers in the guest's order — 0x800521C0, 0x8001F158, 0x8001F798 EmitActorDrawList, 0x800258F0 RenderWorldChunks, 0x8004EBA8 EmitStaticActorMeshList — but every one of them is still produced by the GUEST leg. There is no native draw standing in for them, so there is nothing for a scope to declare; each gets its scope in the commit that gives it a native producer, not before.
  RE-ASKED AND RE-RUN 2026-08-12 17:41 ON A FRESH BUILD, because "can you name more producers" deserves a new measurement rather than a re-reading of this paragraph (scratch/logs/prod61_cap3000.log, cap 300 s, rc=0): `1 row(s); prims seen 1378 = attributed 1378 + unscoped-native 0 + guest-origin 0 + gp0-anon 0 + span-miss 0 + span-no-fn 0` / `guest 0x8007CD38 native 1378 guest 0 frames 696 (f585..f1281) titlefx:spriteEmit`. Still ONE row, still `unscoped-native 0`. One clarification worth adding, because it is the trap in this question: **being natively OWNED is not being a native PRODUCER.** `game/core/native_terrain.cpp` owns 0x8004EBA8 as a byte-exact body, yet 0x8004EBA8 is on the unproduced list above and must be — it writes POLY_F3/FT3 packets into GUEST memory and calls nothing in the render queue (`grep -c 'rq\.\|push2dQuad\|producerScope' game/core/native_terrain.cpp` -> 0), so its prims travel the GUEST leg through the packet-pool span table, where they are counted by OtAttr and not by `noteNative`. Wrapping it in a `ProducerScope` would mint a permanently 0-prim row — the census only ever sees render-queue pushes. That is why "15 full native bodies, several of them renderers" and "exactly one native producer" are both true at once, and it is the distinction to check before adding a scope to any owned renderer.
  SCOPE OF THAT CERTIFICATE: it is the front-end workload (3000 presented fields, stage 13). `unscoped-native 0` is evidence about the prims this run produced, not a proof about code paths it never entered — re-read it on the first run that reaches a level.

WHAT THIS DOES *NOT* GIVE, stated so the row is not over-read: the two legs still cannot be JOINED, because #56 is still open — `GameConfig::packetPoolBase/Stride` are 0, so the guest leg records no spans and the row's `guest 0` is 'not measured', not 'the guest submits nothing here'. The DB can now say WHICH effect has a native producer; it cannot yet COMPARE the two legs' prim counts for that effect. #56 remains the blocker for that, exactly as this issue said.

CLAIM FILE: scratch/producers/claims.txt did not exist before this work and now holds the single line `0x8007CD38`. It is earned from the run JSONL (`loadClaims` accepts a row with prims_native > 0), not hand-written. Note the Tomba2 kanban #91 hazard is REAL here and was observed: `appendClaims` re-appends the whole LOADED set unconditionally, so the file grew a duplicate line per verification run (3 lines for 1 address) before being deduped by hand. Nothing in the file records which build earned it, so if this producer's key ever moves off 0x8007CD38 the line fossilises and the guest leg will resolve to an address no build can earn.
